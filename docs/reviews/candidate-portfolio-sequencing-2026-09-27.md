# Candidate portfolio sequencing and market-access principle

Date: 2026-09-27
Status: **DURABLE SPONSOR / ALLOCATION MEMORY — NOT A SECOND BACKLOG**

## Sponsor correction

The project must not equate:

> **enterprise capability exists**

with:

> **there is no value opportunity for smaller/leaner users**.

A capability can already exist in mature enterprise products and still support a useful product
for another segment if that segment lacks practical access, cannot justify the implementation
overhead, needs only a narrow subset, or values a different combination of evidence transparency,
scope, workflow and cost.

Therefore competitor presence removes **novelty credit**, not automatically **user-value potential**.

## Four questions that must remain separate

1. **Capability existence** — can someone already do this well?
2. **Segment access** — can the target user practically obtain/use that capability?
3. **Operational fit** — is the available capability proportionate to the user's actual job?
4. **User value** — does the candidate reduce consequential burden/risk enough to change behavior?

Needle should use the strongest realistic comparator for the **target segment**, not silently give
a lean-team comparator enterprise infrastructure that the target segment may not actually operate.

This is not permission to cripple baselines.

## Apply the principle to A and C — timing

The **principle** applies to A and C immediately.

The **deep work** should remain sequential.

### Candidate A

Do not assume that because mature legal-evaluation teams can build sophisticated oracle-maintenance
workflows, every smaller legal-tech team or legal department has equivalent internal evaluation
infrastructure.

When Candidate A resumes, explicitly test:

> whether a leaner evaluation owner has the same practical maintenance burden/access gap.

Do not reopen A before B reaches a decision gate unless new evidence materially changes A.

### Candidate C

Do not assume that because mature eval platforms can turn incidents into regression tests, smaller
legal-AI teams have the legal-oracle expertise/process needed to convert a real legal failure into a
safe maintained regression.

When Candidate C receives its turn, explicitly separate:

- generic regression plumbing (already commoditized);
- legal-oracle conversion / evidence / valid-alternative / time-state work;
- accessibility of that capability to smaller teams.

Candidate C may ultimately be especially relevant to lean legal-AI teams, but this should be tested
after B's current loop rather than inferred now.

## Portfolio rule

> **Preserve candidate potential; allocate one active learning loop at a time.**

Not-first does not mean useless.

Competitor existence does not mean no value.

Novelty does not equal value.

Enterprise capability does not equal segment accessibility.

Strong baselines remain mandatory, but must be realistic for the user/job being tested.
