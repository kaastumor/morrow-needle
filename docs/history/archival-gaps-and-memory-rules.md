## 3. Anti-forgetting rule: every contraction needs a preservation record

When a future gate shrinks the project, record all four separately:

1. **CLAIM REJECTED** — what proposition did evidence actually refute?
2. **CAPABILITY PRESERVED** — what code/model/method still works?
3. **DEFAULT STATUS** — current / optional / parked / historical-only;
4. **REACTIVATION CONDITION** — what concrete evidence would justify using it again?

Never write simply 'retired' when the actual evidence means 'technically valid but not currently
worth investing in'.

## 4. Anti-forgetting rule: history is a mandatory orientation source

Before any project-wide direction review, product revival, architecture replacement or claim that
'Needle never built X', inspect:

- `docs/history/README.md`;
- `docs/history/asset-register.md`;
- relevant interface decision record;
- current `BACKLOG.md` and charter;
- the value evidence that parked/rejected the asset.

Historical memory does not override current scope. It prevents false amnesia.

## 5. Anti-forgetting rule: park by pointer, not by disappearance

A parked capability should have:

- canonical code/schema path;
- decision/evidence path;
- concise reason it is parked;
- re-entry condition.

The asset register owns this pointer layer.

## 6. Anti-forgetting rule: preserve exact decisive experiment artifacts

For future decisive evaluations, after blind execution ends preserve:

- exact revealed prompts;
- exact answer/evaluator keys;
- raw outputs;
- score/adjudication record;
- exact evidence owners;
- task/version/commit;
- execution failures separately from subject failures.

If confidentiality prevents repository storage, preserve:

- immutable archive location;
- access boundary;
- identifying hash;
- which claims cannot be independently audited without that archive.

Hashes plus prose summaries are not enough for full reproducibility.

## 7. Anti-forgetting rule: history docs are not current queue

This history package must never become a reason to resume old features automatically.

`BACKLOG.md` owns current work.

History answers:

> What did we know, build, test, park or reject?

Backlog answers:

> What are we doing now?

## 8. Anti-forgetting rule: preserve the distinction between technical and value evidence

Always keep these separate:

- **technical feasibility** — can the system/model represent/do it?
- **scientific validity** — does the evaluation/test support the claim?
- **workflow value** — does it reduce consequential effort/errors versus the incumbent?
- **commercial value** — will a real owner adopt/pay/reuse?

Needle repeatedly had strong technical feasibility and weak incremental product evidence.
Future reviews must not collapse those into either 'everything worked' or 'nothing worked'.

## 9. Anti-forgetting rule: periodic history reconciliation

After any major identity shift, release, MVP gate or retirement programme:

- update this history package if interpretation changed materially;
- update the asset register if status/reactivation changed;
- do not copy mutable counts/WIP into history unless clearly dated;
- add new archival gaps immediately rather than after a later audit discovers them.
