loss in the simpler baseline.

## Cleanness

Current repository surface at this checkpoint:

- 50 JSON schemas;
- 70 Python test files;
- 28 decision records;
- 7 audit records;
- 52 Python source files;
- 12 discovery fixtures.

This is a substantial legal-information model, but there is no evidence-backed

Reasons not to simplify destructively:

- v0.1 contracts retained after v0.2 are provenance/regression artifacts, not
  competing active truth stores;
- new contracts remain narrow owners rather than cross-cutting engines;
- no open issue or broken CI indicates abandoned half-built architecture;
- recent changes repeatedly preserved boundaries between source truth,
  causal truth, temporal truth, geometry and derived evaluation.

## Leanness

The primary lean risk is now **ontology creep through successful discovery**.

The correct control is admission discipline:

1. existing contracts must fail first;
2. the failure must be preserved;
3. one domain-specific case does not automatically justify a generic primitive;
4. a second orthogonal case is normally required before a new causal family is
   frozen;
5. no generic engine should be introduced when a bounded declarative contract
   is sufficient;
6. idle is preferable to speculative architecture.

No new project-management process is required.

## What should not happen next

- no generic rules engine;
- no generic knowledge graph;
- no GIS engine;
- no aviation engine;
- no automatic product resurrection;
- no schema consolidation merely to reduce file count;
- no deletion of historical interfaces that still protect regressions.

## Direction

**continue**

The research thesis is producing repeatable value: official cases are exposing
real legal-information failure modes that the simpler baseline contracts cannot
always represent safely.

The next task should still begin from a fresh, falsifiable legal-information
question. The backlog should remain empty between such questions.
